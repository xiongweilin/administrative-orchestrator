# M8 — Document-Driven Organizational Transactions

Status: **accepted for the recorded isolated-staging/document-driven transaction
scope; candidate PR checks passed; merge and M9 remain out of scope**

M8 turns trusted intake evidence into bounded organizational transaction
preparation while preserving the M5–M7 authority and execution boundaries.
The milestone does not create a finance authority plane or a payment system.

## Supported cases

| Case kind | Preparation effects | Forbidden effects |
| --- | --- | --- |
| `procurement-request` | purchase-order draft and bounded confirmation | payment, settlement, bank transfer |
| `invoice-ap-preparation` | vendor-bill draft after qualification/match | posting payment, settlement |
| `expense-reimbursement` | expense record/report preparation | reimbursement payment, bank transfer |

All cases retain the existing sequence:

```text
trusted artifact
→ immutable representation
→ evidence spans / candidate claims
→ human admission
→ typed facts and policy evaluation
→ qualification assessment
→ decision and governance basis
→ frozen obligations
→ Kernel-owned effect
→ independent ERP readback
→ exact outcome binding
→ Administrative completion or reopen/reconcile
```

## Durable foundations

- `DocumentRepresentation` preserves parser/OCR output as immutable,
  content-addressed data. The current bounded parser supports text-bearing PDFs
  and plain text; OCR remains explicitly deferred.
- `EvidenceSpan.representation_ref` is nullable for historical M5/M6 data and
  is populated for new derived spans.
- `AdministrativeCaseEvidenceLink` records the case, authority epoch, raw
  artifact, optional representation, declared role, source, and linker.
- `TransactionQualificationAssessment` records qualification result, rule,
  input references, blockers, and authority epoch.
- `Money` rejects binary floats and normalizes currency to a three-letter code.

## Gates

The staging checklist uses the following gates:

- A–C: isolated topology, migration/bootstrap, and version pin verification;
- D–F: authenticated intake, artifact/representation lineage, and bounded
  parser failures;
- G–I: human admission, typed policy evaluation, and current governance;
- J–L: vendor qualification, duplicate detection, and invoice three-way match;
- M–O: obligation immutability, Kernel capability routing, and ERP draft-only
  execution;
- P–R: independent readback, unknown/mismatch recovery, and exact completion
  binding;
- S: no-payment/no-settlement proof, audit/observability, rollback, and
  preserved historical M5–M7 evidence.

The final acceptance record is created only after a fresh isolated staging run
with real provider credentials and redacted evidence. Missing credentials or a
provider that cannot supply durable identity/readback is recorded as a gate
blocker; mocks do not substitute for that boundary.

The current record is `docs/acceptance/M8-staging-acceptance.md`. It records
local real-provider evidence and candidate-specific remote PASS evidence for
the bounded M8 scope, including the runtime Kernel revision invariant, exact
effect/realization/outcome completion binding, and cross-repository restart and
recovery checks. The candidate branches are pushed as Admin PR #80 and Kernel
PR #99. M8 is accepted for this recorded scope; merge is a separate action and
M9 does not begin from this milestone.

## Non-goals

No bank transfer, payment, settlement, generic RAG, new repository, meta-
controller, historical acceptance rewrite, standing public staging entry, or
automatic human approval is introduced by M8.
