# M5 — Production Trust & Reality Integration

M5 moves the administrative reference system from a governed sandbox/reference topology to a production-shaped trust and reality boundary. It does not change the ownership model established in M4.

## Objective

A production deployment must be able to answer, with durable evidence:

1. who the caller is and which current organizational principal that identity resolves to;
2. which facts are claims versus authoritative external observations;
3. which policy/approval basis authorized the business action;
4. which Agent Kernel Work/Attempt crossed the physical RealityBoundary;
5. whether an external provider result is succeeded, failed, unavailable, or execution-unknown;
6. whether an independent verifier observed the declared business postcondition;
7. how the system recovers after process, provider, database, or operator interruption without inventing retry authority.

## Ownership invariants preserved from M4

These remain non-negotiable:

```text
Administrative business authority != Agent Kernel runtime authority
Administrative obligation != Kernel Work
Kernel evidence != Administrative ConfirmedOutcome
connector success != verified business completion
execution-unknown != retry permission
Kernel remains the unique physical RealityBoundary for cut-over writes
```

DBOS remains the durable wait/replay mechanism. `AdministrativeCase` remains the business state machine. External identity providers authenticate; they do not directly mint Administrative roles or approval authority.

## Implemented production-trust slices

### Identity and authentication

- Production `Settings` require OIDC/JWKS asymmetric verification.
- Production OIDC issuer must use HTTPS.
- Allowed production signing algorithms are restricted to `RS256` and `ES256`.
- External OIDC subjects resolve through durable `IdentityBinding` history instead of caller-supplied principal IDs.
- Binding, revocation, controlled non-overlapping rebind, and principal deactivation are explicit audited lifecycle events.
- IdP groups/roles remain separate from Administrative authority records.

### Authoritative facts

- `FactAssertion` provides field-level authority and provenance.
- Mixed snapshots stay conservatively `CLAIM` at the aggregate level; authoritative HRIS fields do not promote request-only fields.
- Odoo HRIS reads preserve source, source identity, version, observation time, and digest.
- Current authoritative HRIS truth is re-read before governed execution/verification transitions.
- Changed, stale, missing, or rebound authoritative truth forces `GOVERNANCE_STALE` reopen rather than continuing under an obsolete basis.

### Production reality connectors

- Odoo HRIS and Keycloak IAM writers carry durable request identity into the external system.
- Transport ambiguity and provider 5xx outcomes become `UNKNOWN`, never automatic retry permission.
- Reconciliation uses durable request identity and rejects duplicate external identities.
- Independent readback verifier identities are separate from writer identities.
- Verification compares observed external reality with the declared postcondition; expected data is not copied into the observed result.

### Human exception operations

- A separate Operations API exposes governed inspection, authoritative fact refresh, identity lifecycle operations, and authority-event history.
- The Operations Console uses OIDC Authorization Code flow and bearer tokens.
- No force-complete, mark-success, evidence override, Kernel authorization, or blind provider retry controls exist.

### Observability

- Every observed HTTP response receives `X-Correlation-ID`; valid caller correlation IDs are propagated and invalid values are replaced.
- Correlation IDs are structured log fields, not Prometheus labels.
- Low-cardinality metrics cover HTTP request count/latency, authoritative fact refresh, governance revalidation, connector outcome, and identity lifecycle events.
- `/metrics` is exposed by the observed API wrappers.

### Production deployment and recovery

- `production_readiness.py` validates production control-plane and connector isolation requirements.
- `scripts/production_preflight.py` verifies deployment configuration, credential references, and the durable Kernel state path without printing secret values.
- Administrative and DBOS durable stores are required to be PostgreSQL for the production control plane.
- Agent Kernel currently uses its canonical bounded-domain-effect SQLite recovery store in a single-writer deployment with durable storage.
- Kernel state backup uses SQLite online backup semantics, `PRAGMA quick_check`, atomic replacement, and a SHA-256 sidecar manifest.
- PostgreSQL DR CI performs a real custom-format `pg_dump`, destroys the current schema, restores it, and verifies semantic identity/lifecycle state.

## Supported Agent Kernel baseline

The Administrative production contract is pinned to:

```text
fe4b3f4bf2e376bd7105caf7d15d77e2483c7197
```

This revision includes the post-action qualification replay fix required by the promoted-Kernel real-staging pre-receipt counterexample: after a Kernel-proven committed action boundary and fresh fencing generation, recovery replays the historical pre-action qualification closure rather than minting a new closure from already-consumed AuthorizationUse.

CI has two distinct responsibilities:

- `kernel-pinned-cutover` proves the supported production baseline;
- the existing full `kernel-cutover-integration` checks current `agent-kernel/main` as a forward-compatibility canary, including lost ACK, pre-receipt crash, durable reconciliation identity, and ambiguous-result recovery.

A green main-canary does not silently change the supported production revision. Promotion requires an explicit Administrative change.

## Initial production SLO targets

These are operating targets, not claims that public CI has measured production traffic:

| Signal | Initial target | Evidence source |
| --- | --- | --- |
| Administrative API availability | >= 99.9% monthly | HTTP request metrics / platform health |
| HTTP GET p95 | < 1 s | `administrative_http_request_duration_seconds` |
| HTTP POST p95 | < 5 s | same metric, including governed writes/refresh |
| Authoritative refresh transport/config failures | < 1% when provider is declared healthy | authoritative refresh counter + provider telemetry |
| Connector `UNKNOWN` outcomes | < 0.1% of production invokes | connector outcome metric / Kernel Attempt evidence |
| Recovery from execution-unknown | no duplicate physical effect | Kernel reconciliation evidence + external request identity |
| Target RPO | <= 5 min | infrastructure backup policy |
| Target RTO | <= 30 min | restore exercise |

`GOVERNANCE_STALE` is not an availability error. It is a correctness signal that must remain visible rather than being optimized away.

## Real staging acceptance boundary

Repository CI cannot truthfully prove enterprise OIDC, Odoo, Keycloak, network policy, or production credential scopes without real staging credentials and reachable staging systems. M5 therefore has an explicit external acceptance boundary.

Before declaring the milestone fully production-accepted, a staging operator must prove all of the following with non-production enterprise accounts:

1. OIDC discovery/JWKS validation, token expiry, wrong audience, unknown subject, revoked binding, and principal deactivation all fail closed.
2. Odoo authoritative reads return the expected employee/department/manager identity and provenance.
3. Odoo writer and verifier run under different least-privilege accounts.
4. Keycloak writer and verifier run under different least-privilege clients.
5. An injected post-write transport failure becomes execution-unknown, then reconciliation discovers the already-created external object without a second create.
6. Independent readback detects an intentionally changed department/access postcondition.
7. An HRIS fact change between authorization and execution causes Administrative reopen before further reality mutation.
8. Operations Console sign-in and exception inspection work through the real staging IdP; no authority shortcut is exposed.
9. Prometheus scraping and structured logs preserve correlation without high-cardinality identity labels.
10. PostgreSQL and Kernel-state restore exercises satisfy the deployment's declared RPO/RTO.

Until this checklist is executed against real staging on the currently supported Kernel baseline, the correct status is **implementation/CI complete; real-staging acceptance pending**.

## Non-goals

M5 does not:

- make IdP groups authoritative Administrative roles;
- let AI mint organizational authority;
- let the Administrative service directly own physical provider retry semantics;
- treat provider HTTP success as business completion;
- introduce a second generic Agent runtime;
- claim multi-writer/active-active support for the current Kernel SQLite state store.

The next storage evolution, if required by measured availability/concurrency needs, should implement the Agent Kernel store port rather than embedding an ad-hoc second runtime store in this repository.
