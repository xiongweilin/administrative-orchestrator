# M6 — Trusted Perception & Admission

Status: In progress. PR1 through PR8 are merged; PR9 adds the Feishu Inbox
provider boundary and asynchronous source-to-candidate pipeline; PR10 adds
the review surface and human-confirmed admission bridge; PR11 adds the
content-addressed document/attachment foundation; the merged attachment slice
wires Feishu canonical file/image resources into that processor. PR12 is the
documentation and acceptance-closure slice. M6 is not complete until the real
provider to M5 vertical slice, applicable document foundation evidence, staging
evidence, and final main CI gates pass.

## Objective

M5 answered:

```text
Does the system have the authority to change reality safely?
```

M6 adds the upstream question:

```text
When does information from non-structured reality qualify to enter the
Administrative formal model?
```

M6 builds trusted perception, candidate interpretation, identity resolution,
assessment, and explicit admission. It does not enlarge Agent Kernel
authority, create an autonomous meta-controller, or expand several new
Administrative domains at once.

The contract and ownership decision are in
[`ADR 0003`](../adr/0003-trusted-perception-and-admission.md).

## Scope boundary

In scope:

- one Administrative Intake Plane inside this product monorepo;
- authenticated provider-event capture and durable delivery idempotency;
- immutable source artifacts, evidence spans, and append-only interpretations;
- candidate requests, candidate facts, candidate case updates, and assessment;
- explicit human-confirmed promotion into the existing M5 request/case path;
- one real Inbox provider reference slice;
- document attachment evidence foundation;
- meeting contract/shadow support only;
- intake review in the existing Operations Console;
- counterexample-based M6 acceptance evidence.

Out of scope:

- a second Work runtime, RealityBoundary, authorization, retry, or completion
  authority;
- automatic case amendment, business decision, finance/AP execution,
  offboarding, procurement, leave, or other M7+ domain expansion;
- three new repositories, generic RAG/vector infrastructure, or a generic
  agent framework;
- production Meeting Agent or transcript-to-Work behavior;
- modifying `agent-kernel` or `meta-controller` for Administrative convenience.

## Canonical chain

```text
provider authenticity
        -> IntakeReceipt
        -> SourceArtifact
        -> EvidenceSpan
        -> InterpretationRecord
        -> CandidateAdministrativeRequest / CandidateCaseUpdate /
           CandidateFactAssertion
        -> IntakeAssessment
        -> PromotionRecord
        -> existing IngressReceipt / AdministrativeRequest
        -> existing M5 AdministrativeCase and trusted-action path
```

The source, interpretation, candidate, and assessment layers are not
authoritative Administrative facts. Promotion is the explicit boundary into
the M5 model.

## Durable contract set

The implementation is expected to add these nine durable objects:

1. `IntakeReceipt` — unique provider delivery identity;
2. `SourceArtifact` — captured source metadata and immutable provenance;
3. `EvidenceSpan` — exact source representation locator;
4. `InterpretationRecord` — append-only structured model/parser output;
5. `CandidateFactAssertion` — candidate-only fact assertion;
6. `CandidateAdministrativeRequest` — candidate request interpretation;
7. `CandidateCaseUpdate` — reviewable update after a conversation is bound;
8. `IntakeAssessment` — disposition and basis;
9. `PromotionRecord` — candidate-to-M5 admission lineage.

Candidate authority is restricted to `CLAIM` and
`ATTESTED_CANDIDATE`. `AUTHORITATIVE` is not part of the candidate type
surface. Existing `FactAuthority.AUTHORITATIVE` remains owned by approved
authoritative sources such as HRIS, IAM, ERP, or another explicitly approved
system of record.

### Identity and conversation semantics

`ConversationRef` is the provider/tenant/thread identity. A provider-native
sender is resolved through the current Administrative `IdentityBinding`; a
displayed sender label is retained as source evidence and never becomes a
Principal. The durable conversation timeline rejects tenant rebound,
unbound senders, sender or participant changes, and out-of-order delivery.

Before admission, an explicitly superseding candidate marks its predecessor
`SUPERSEDED` while retaining the predecessor history. After admission, a new
message is attached to the existing case as a human-reviewable
`CandidateCaseUpdate`; it cannot create a second case. These semantics are
implemented in `conversation.py` and migration `0017_m6_conversation`.

The Operations API exposes the review queue and candidate detail, records a
final human `IntakeAssessment`, and promotes only through the existing
idempotent admission service. The console never accepts model confidence as
authority and requires explicit source/event/requester identity before
promotion.

### Feishu provider v1 and durable ingress

PR9 selects Feishu as the reference Inbox provider because the local
`feishu-dify-gateway` already owns a documented official SDK long-connection
transport and provider authenticity boundary. The Administrative adapter is
deliberately a separate compatibility surface: it verifies the token carried
by the trusted long-connection metadata handoff, stores only delivery metadata
in the receipt and outbox payload, and performs canonical message retrieval in
the asynchronous pipeline. The metadata boundary never calls the canonical
fetcher, model gateway, or candidate projection service.

The durable handoff is:

```text
verified Feishu long-connection event metadata
  -> IntakeReceipt + intake.feishu.received outbox event (one transaction)
  -> canonical Feishu message fetch
  -> ArtifactStore + SourceArtifact + EvidenceSpan
  -> current IdentityBinding resolution
  -> InterpretationRecord
  -> CandidateAdministrativeRequest
  -> ConversationMessage
```

The provider adapter stores no message body in the receipt or outbox payload.
Canonical fetch failure, unbound identity, invalid model output, and model
provider failure preserve the source lineage and do not fabricate admission.
The metadata handoff responds after the verified metadata transaction; it does not wait
for canonical fetch, model inference, candidate projection, or review. The
configured runtime builds the boundary and worker pipeline from deployment
settings, while a Feishu outbox event fails closed and remains retryable if
processing dependencies are absent. The repository contains this runtime
boundary; it does not claim that a real Feishu long connection, canonical
provider credential, or staging route has been exercised.

### Human-confirmed `bridge_to_m5`

The Operations API keeps review and admission distinct:

1. an authorized intake reviewer reads the candidate and records a final
   human `IntakeAssessment(ADMIT)` with a non-empty basis;
2. promotion references that assessment and the verified source identity;
3. `bridge_to_m5=true` is accepted only for `employee-onboarding` and a
   human-selected non-blank `subject_ref`;
4. the onboarding admission service creates the normal promotion and M5
   request/case lineage and evaluates the current onboarding policy.

The bridge is explicit, idempotent, and auditable. It does not infer
authority from model confidence, does not create a second Work runtime, and
does not call Kernel or external providers directly. The candidate facts
entered into the M5 snapshot remain `FactAuthority.CLAIM`, including after
human confirmation. A replay of the same source identity returns the existing
promotion/request/case; conflicting requester or lineage input fails closed.

### Candidate `CLAIM` and authoritative refresh boundary

Candidate facts can only be `CLAIM` or `ATTESTED_CANDIDATE`; the candidate
surface cannot construct `AUTHORITATIVE`. The human-confirmed bridge grants
permission for a candidate request to enter the existing M5 workflow, not
permission to assert that the candidate facts are true in an external system
of record.

Authoritative onboarding fields are acquired separately from the approved HRIS
reader by the existing operations refresh and execution revalidation paths.
That path overlays approved HRIS fields as `AUTHORITATIVE`, leaves
request-only fields such as requested systems as claims, and re-evaluates the
policy. Stale or changed authoritative dependencies block continuation and
use the existing `GOVERNANCE_STALE` reopen/reassessment behavior. A successful
candidate bridge alone is never evidence of an Odoo, Keycloak, or Kernel
read/write result.

### Document attachment foundation

PR11 provides the `ArtifactStore` foundation used by source artifacts and
evidence spans. The current filesystem/staging adapter stores raw bytes outside
PostgreSQL under content-addressed SHA-256 references, publishes new objects
atomically, and verifies the digest on reads. PostgreSQL retains only the
source metadata, MIME/size, provenance, storage reference, digest, evidence
locator, and interpretation lineage.

The Feishu provider integration now supplies canonical file/image bytes to this
processor, and the production worker's artifact root is backed by a named
durable volume. This is not a claim that a real provider attachment run, OCR,
document interpretation, or document-to-Work behavior has passed staging.
Missing, corrupt, or unavailable artifact storage fails closed and cannot
fabricate an interpretation or admission. The staging template includes a
non-sensitive integrity check that must use a fixture digest/reference rather
than a document body.

## Rollout states

```text
SHADOW -> HUMAN_CONFIRMED -> BOUNDED_AUTO_ADMISSION
```

The M6 reference path is `HUMAN_CONFIRMED`. Shadow processing may capture
source, interpretation, candidate, and a recommendation but must not create
an `AdministrativeRequest`. Bounded auto-admission is not enabled by default
and may only be introduced behind an explicit policy after evidence exists.

## Acceptance gates

The implementation must record evidence for at least:

| Gate | Required proof |
| --- | --- |
| A — Source authenticity | The official SDK long connection delivers a real event; valid metadata/token is accepted, wrong or missing token is rejected, forged metadata creates no receipt, and tenant rebound fails closed. URL verification/signed HTTP callback is `N/A` unless separately enabled |
| B — Interpretation provenance | Same artifact supports model/profile v1 and v2 without mutation or loss of v1 |
| C — AI authority isolation | Prompt-injection source remains candidate-only and cannot mint facts, decisions, grants, Work, or effects |
| D — Identity | Displayed sender is not Principal; provider identity resolves through tenant and current Administrative IdentityBinding |
| E — Conversation | Pre-admission candidates supersede explicitly; post-admission message becomes reviewable `CandidateCaseUpdate`, not a second case |
| F — Promotion idempotency | Concurrent/redelivered admission yields at most one `AdministrativeRequest` and one case |
| G — Crash recovery | Persisted event resumes after restart without duplicate receipt/request/case |
| H — Model failure | Source remains retained and admission is not fabricated when the model is unavailable or invalid |
| I — Prompt injection | Untrusted content cannot call tools, change roles, mint authority, or perform reality effects |
| J — Real end-to-end intake | Real staging provider delivery reaches review, human-confirmed admission, and the existing M5 Odoo/Keycloak/Kernel/verification path; this is not proven by repository tests |
| K — Artifact integrity foundation | A non-sensitive staging fixture is stored, read back, and digest-verified; corruption/missing-object behavior fails closed; no raw body is copied into the evidence record |

## Delivery slices

The M6 work is intentionally split into small, independently reviewable
slices:

1. Contract and ADR (this document; no provider implementation).
2. Durable Intake Core and Alembic migration.
3. Typed invariants and negative/conformance tests.
4. `ArtifactStore` port and integrity-tested adapter.
5. Model Gateway/Interpretation port and failure/prompt-injection tests.
6. Deterministic assessment and idempotent promotion.
7. Identity and conversation semantics.
8. Operations Console Intake Review.
9. One real Inbox provider (Feishu adapter and durable async pipeline).
10. Real Inbox human-confirmed vertical slice.
11. Document attachment evidence foundation.
12. M6 real-staging acceptance and documentation closure.

Each slice must state its authority non-goals, migration impact, failure and
recovery semantics, direct tests, and the next remaining slice. No slice may
silently introduce M7–M10 behavior.

## M5 regression matrix

M6 is intake-only unless a change crosses an existing M5 trust boundary.
Rerun the relevant M5 evidence when:

- the supported Kernel pin or Kernel bridge changes;
- OIDC/authentication/JWKS changes;
- Odoo/Keycloak reader, writer, verifier, or reconciliation behavior changes;
- artifact storage topology changes;
- the intake path changes a production trust boundary.

Otherwise run the M6 intake gates and normal affected repository CI; do not
replace real-staging evidence with unit tests when the M5 boundary changed.

## Evidence and completion

M6 completion requires implementation and evidence, not a design-only claim.
The acceptance record under `docs/acceptance/` must not contain secrets,
provider tokens, credential values, or sensitive source/document bodies. Use
stable redacted identifiers, digests, configuration references, timestamps,
and links to access-controlled evidence where needed. The final report may
claim completion only when all M6 success-definition items are proven,
required CI is green, the final changes are merged to `main`, post-merge main
CI is green, and the real-staging record is complete. Until then, M6 remains
incomplete.
