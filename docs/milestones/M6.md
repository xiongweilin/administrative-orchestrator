# M6 — Trusted Perception & Admission

Status: In progress. PR1 contract and PR2 durable core are merged; PR3 adds
the candidate-only conformance boundary. M6 is not complete until the remaining recorded implementation,
real provider vertical slice, document foundation, staging evidence, and
final main CI gates pass.

## Objective

M5 answered:

```text
Does the system have the authority to change reality safely?
```

M6 adds the upstream question:

```text
When does information from non-structured reality qualify to enter the
Administrative formal model?
```

M6 builds trusted perception, candidate interpretation, identity resolution,
assessment, and explicit admission. It does not enlarge Agent Kernel
authority, create an autonomous meta-controller, or expand several new
Administrative domains at once.

The contract and ownership decision are in
[`ADR 0003`](../adr/0003-trusted-perception-and-admission.md).

## Scope boundary

In scope:

- one Administrative Intake Plane inside this product monorepo;
- authenticated provider-event capture and durable delivery idempotency;
- immutable source artifacts, evidence spans, and append-only interpretations;
- candidate requests, candidate facts, candidate case updates, and assessment;
- explicit human-confirmed promotion into the existing M5 request/case path;
- one real Inbox provider reference slice;
- document attachment evidence foundation;
- meeting contract/shadow support only;
- intake review in the existing Operations Console;
- counterexample-based M6 acceptance evidence.

Out of scope:

- a second Work runtime, RealityBoundary, authorization, retry, or completion
  authority;
- automatic case amendment, business decision, finance/AP execution,
  offboarding, procurement, leave, or other M7+ domain expansion;
- three new repositories, generic RAG/vector infrastructure, or a generic
  agent framework;
- production Meeting Agent or transcript-to-Work behavior;
- modifying `agent-kernel` or `meta-controller` for Administrative convenience.

## Canonical chain

```text
provider authenticity
        -> IntakeReceipt
        -> SourceArtifact
        -> EvidenceSpan
        -> InterpretationRecord
        -> CandidateAdministrativeRequest / CandidateCaseUpdate /
           CandidateFactAssertion
        -> IntakeAssessment
        -> PromotionRecord
        -> existing IngressReceipt / AdministrativeRequest
        -> existing M5 AdministrativeCase and trusted-action path
```

The source, interpretation, candidate, and assessment layers are not
authoritative Administrative facts. Promotion is the explicit boundary into
the M5 model.

## Durable contract set

The implementation is expected to add these nine durable objects:

1. `IntakeReceipt` — unique provider delivery identity;
2. `SourceArtifact` — captured source metadata and immutable provenance;
3. `EvidenceSpan` — exact source representation locator;
4. `InterpretationRecord` — append-only structured model/parser output;
5. `CandidateFactAssertion` — candidate-only fact assertion;
6. `CandidateAdministrativeRequest` — candidate request interpretation;
7. `CandidateCaseUpdate` — reviewable update after a conversation is bound;
8. `IntakeAssessment` — disposition and basis;
9. `PromotionRecord` — candidate-to-M5 admission lineage.

Candidate authority is restricted to `CLAIM` and
`ATTESTED_CANDIDATE`. `AUTHORITATIVE` is not part of the candidate type
surface. Existing `FactAuthority.AUTHORITATIVE` remains owned by approved
authoritative sources such as HRIS, IAM, ERP, or another explicitly approved
system of record.

## Rollout states

```text
SHADOW -> HUMAN_CONFIRMED -> BOUNDED_AUTO_ADMISSION
```

The M6 reference path is `HUMAN_CONFIRMED`. Shadow processing may capture
source, interpretation, candidate, and a recommendation but must not create
an `AdministrativeRequest`. Bounded auto-admission is not enabled by default
and may only be introduced behind an explicit policy after evidence exists.

## Acceptance gates

The implementation must record evidence for at least:

| Gate | Required proof |
| --- | --- |
| A — Source authenticity | Valid event accepted; invalid signature/token rejected; duplicate delivery produces one receipt; tenant rebound fails closed |
| B — Interpretation provenance | Same artifact supports model/profile v1 and v2 without mutation or loss of v1 |
| C — AI authority isolation | Prompt-injection source remains candidate-only and cannot mint facts, decisions, grants, Work, or effects |
| D — Identity | Displayed sender is not Principal; provider identity resolves through tenant and current Administrative IdentityBinding |
| E — Conversation | Pre-admission candidates supersede explicitly; post-admission message becomes reviewable `CandidateCaseUpdate`, not a second case |
| F — Promotion idempotency | Concurrent/redelivered admission yields at most one `AdministrativeRequest` and one case |
| G — Crash recovery | Persisted event resumes after restart without duplicate receipt/request/case |
| H — Model failure | Source remains retained and admission is not fabricated when the model is unavailable or invalid |
| I — Prompt injection | Untrusted content cannot call tools, change roles, mint authority, or perform reality effects |
| J — Real end-to-end intake | One real provider completes human-confirmed onboarding through the existing M5 Odoo/Keycloak/Kernel/verification path |

## Delivery slices

The M6 work is intentionally split into small, independently reviewable
slices:

1. Contract and ADR (this document; no provider implementation).
2. Durable Intake Core and Alembic migration.
3. Typed invariants and negative/conformance tests.
4. `ArtifactStore` port and integrity-tested adapter.
5. Model Gateway/Interpretation port and failure/prompt-injection tests.
6. Deterministic assessment and idempotent promotion.
7. Identity and conversation semantics.
8. Operations Console Intake Review.
9. One real Inbox provider.
10. Real Inbox human-confirmed vertical slice.
11. Document attachment evidence foundation.
12. M6 real-staging acceptance and documentation closure.

Each slice must state its authority non-goals, migration impact, failure and
recovery semantics, direct tests, and the next remaining slice. No slice may
silently introduce M7–M10 behavior.

## M5 regression matrix

M6 is intake-only unless a change crosses an existing M5 trust boundary.
Rerun the relevant M5 evidence when:

- the supported Kernel pin or Kernel bridge changes;
- OIDC/authentication/JWKS changes;
- Odoo/Keycloak reader, writer, verifier, or reconciliation behavior changes;
- artifact storage topology changes;
- the intake path changes a production trust boundary.

Otherwise run the M6 intake gates and normal affected repository CI; do not
replace real-staging evidence with unit tests when the M5 boundary changed.

## Evidence and completion

M6 completion requires implementation and evidence, not a design-only claim.
The final acceptance record under `docs/acceptance/` must not contain secrets
or sensitive source bodies. The final report may claim completion only when
all M6 success-definition items are proven, required CI is green, the final
changes are merged to `main`, and post-merge main CI is green.
